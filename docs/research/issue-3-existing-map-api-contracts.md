# Issue #3 research: existing map and Journey Planning API contracts

Status: Historical Research

Research date: 2026-08-29
Scope: Primary-source comparison of Apple MapKit, Google Routes API, Mapbox Directions API, and OpenTripPlanner (OTP) as precedents for Via's shared Swift/Kotlin Journey Planning contract.

## Decision

No reviewed API is a contract Via can adopt unchanged.

- Use OTP's platform-neutral labeled-coordinate input, Journey Option–Leg hierarchy, typed routing errors, semantic Guidance components, and separation of scheduled from estimated transit time as the closest structural precedent.
- Use Google and Mapbox as precedents for explicit time/locale fields, compact versioned geometry, and machine-readable warnings or errors.
- Treat MapKit only as an iOS adapter and presentation precedent. `MKMapItem`, Apple-generated instruction strings, and framework types must stop at the native-client boundary.
- Improve on all four contracts by returning the immutable Network Snapshot identifier, Live Status observation times and Freshness, actual YouBike pickup and return counts, and versioned semantic codes. None of the reviewed hosted directions contracts exposes enough evidence to support Via's Reliable/Feasible distinction.
- Refresh an open result by repeating the complete Planning Request and atomically replacing the result. Do not copy leg-only mutation or navigation-session refresh patterns.

## Apple MapKit: useful native precedent, wrong shared boundary

Apple defines `MKDirections.Request` as start/end points plus a planned conveyance. Its `source` and `destination` are `MKMapItem` values; the request also supports transport type, alternate routes, and departure or arrival dates. `MKDirections.Response` returns source, destination, and an array of routes. Each `MKRoute` has route-level geometry, steps, distance, expected travel time, transport type, and advisory strings; each step has geometry, a written instruction, an optional notice, distance, and transport type. Calling `calculate` starts a new asynchronous computation, and calling it while the same object is already calculating produces an error. [Apple `MKDirections.Request`](https://developer.apple.com/documentation/mapkit/mkdirections/request), [response](https://developer.apple.com/documentation/mapkit/mkdirections/response), [`MKRoute`](https://developer.apple.com/documentation/mapkit/mkroute), [`MKRoute.Step`](https://developer.apple.com/documentation/mapkit/mkroute/step), [`calculate`](https://developer.apple.com/documentation/mapkit/mkdirections/calculate(completionhandler:))

This is a good shape for an iOS adapter: selected MapKit search output can supply a coordinate and display label, and returned Via geometry can become native overlays. It is a poor wire contract because `MKMapItem`, `MKPolyline`, framework error types, and Apple-authored instruction strings have no Kotlin equivalent and would bind Via to Apple's place and localization behavior.

MapKit also lacks Via's required concepts: independent transit-mode filters, a typed multimodal Leg model, Network Snapshot identity, Live Status observation time/Freshness, actual YouBike pickup and return evidence, and stable semantic warning/Guidance codes. Absence from the public client API must not be interpreted as fresh or normal evidence.

## Google Routes API: explicit wire fields, incomplete evidence

`computeRoutes` is an explicit `POST` to `/directions/v2:computeRoutes`. It requires origin and destination waypoints, supports intermediate waypoints, alternate routes, one top-level travel mode, mutually exclusive departure/arrival timestamps, `languageCode`, units, transit preferences, and a required response field mask. A waypoint may be a coordinate, a Google Place ID, or a human-readable address. Transit preferences can allow Bus, subway, train, light rail, or rail and can express fewer-Transfer or less-Walking preferences. [Google `computeRoutes`](https://developers.google.com/maps/documentation/routes/reference/rest/v2/TopLevel/computeRoutes), [`Waypoint`](https://developers.google.com/maps/documentation/routes/reference/rest/v2/Waypoint), [`TransitPreferences`](https://developers.google.com/maps/documentation/routes/reference/rest/v2/TransitPreferences)

The response hierarchy is route → Leg → step. Geometry can be encoded polyline or GeoJSON. Steps expose a travel-mode enum, geometry, navigation instruction and transit details; transit details include boarding/alighting stops and times, headway, line, and vehicle metadata. The navigation instruction includes a machine maneuver enum as well as rendered instruction text, while duration and distance also have localized forms. [Google route, Leg, step, transit, and polyline types](https://developers.google.com/maps/documentation/routes/reference/rest/v2/TopLevel/computeRoutes#Route)

Useful Via precedents are explicit offset-aware timestamps, a BCP 47 language field, typed transit-mode filters, a typed geometry union, nested transit facts, structured travel advisories, and field selection. Patterns to avoid are provider place IDs/addresses in the Via request, one mutually exclusive top-level travel mode, provider-rendered text as authoritative Guidance, and treating returned transit event times as freshness proof. The documented route result has no general observation timestamp, freshness evaluation, immutable source snapshot, or bike-share availability.

## Mapbox Directions API: strong geometry and warning mechanics, no transit model

Mapbox Directions v5 takes two or more ordered `longitude,latitude` pairs in the URL and selects one routing profile: driving, driving-traffic, Walking, or cycling. It can return up to two alternatives. Optional parameters select steps, language, route/step geometry as GeoJSON, polyline5, or polyline6, and overview detail. Custom waypoint names feed rendered arrival, banner, and voice instructions. Reference departure/arrival time options are profile-limited. [Mapbox Directions API](https://docs.mapbox.com/api/navigation/directions/)

The response uses route → Leg → step, with maneuver/location fields, geometry, instructions, and annotations. Its notification model is a useful precedent: a notification has machine type/subtype, optional geometry scope, reason/details, and a `refresh_type` that distinguishes persistent static facts from dynamic facts replaced during a route refresh. Its error contract also separates a machine `code` from an optional human `message`, though `NoRoute` and `NoSegment` are returned with HTTP 200. [Mapbox route notifications and errors](https://docs.mapbox.com/api/navigation/directions/#notification-object)

Via should adopt explicit geometry encoding/precision and scoped machine warnings, but not Mapbox's URL-carried coordinates, single-profile mode model, English fallback, prose instruction authority, or navigation-session partial refresh. The Directions API has no public-transit Journey hierarchy or bike-share inventory, and cycling routing is not YouBike availability.

## OpenTripPlanner: closest semantic precedent

OTP's current `planConnection` request takes required `origin` and `destination` labeled locations. A labeled location is an optional display label plus a platform-neutral location; the location may be WGS84 coordinates or a transit stop. Time is a one-of earliest-departure/latest-arrival value, modes distinguish direct from transit use, and locale is explicit or supplied through `Accept-Language`. OTP notes that a translation may be unavailable. [OTP `planConnection`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/queries/planConnection), [`PlanLabeledLocationInput`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/PlanLabeledLocationInput), [`PlanDateTimeInput`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/PlanDateTimeInput), [`PlanModesInput`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/PlanModesInput)

The result contains itinerary edges, pagination metadata, effective search time, and typed routing errors. Each itinerary supplies timezone-aware start/end, duration, Transfers, Walking/waiting facts, and ordered Legs. A Leg supplies mode, endpoints, scheduled and estimated times, route/trip data, stop calls, alerts, geometry, and Guidance steps. Geometry is a Google-encoded polyline plus point count. Guidance steps expose semantic relative/absolute directions, distance, street, exit, and flags rather than requiring one rendered sentence. [OTP `PlanConnection`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/PlanConnection), [`Itinerary`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/Itinerary), [`Leg`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/Leg), [`Geometry`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/Geometry), [Guidance `step`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/step)

OTP cleanly separates required scheduled time from an optional real-time estimate and exposes typed trip states such as updated, canceled, added, or modified. Rental stations expose pickup/drop-off permission, operative state, and vehicles/spaces by type. However, OTP explicitly documents that counts can be synthetic when `realtime=false`; its planned estimates and rental counts do not form a general observation-time/Freshness contract. [OTP `LegTime`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/LegTime), [`RealTimeTripState`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/RealTimeTripState), [`VehicleRentalStation`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/VehicleRentalStation)

OTP's `RoutingError` contains a code, description, and input field, and its documentation explicitly says clients should translate user-visible errors from the code. Alerts are separately structured, scoped, effective-dated, severity-bearing, and localized. This is the strongest direct precedent for Via's code-plus-typed-parameters contract. [OTP `RoutingError`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/RoutingError), [`Alert`](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/Alert)

OTP exposes `/otp/gtfs/v1`, evolves GraphQL fields through deprecation, and has removed older APIs over major releases. Its Leg refetch identifier is intentionally not durable and may stop resolving after hours; cursor pagination searches earlier/later time windows rather than refreshing the same result. Via should therefore use its own versioned semantic matching key only where safe and repeat the complete Planning Request for refresh. [OTP GraphQL introduction](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/introduction), [Leg identifier](https://docs.opentripplanner.org/api/dev-2.x/graphql-gtfs/types/Leg), [OTP changelog](https://docs.opentripplanner.org/en/latest/Changelog/)

## Recommended contract consequences for issue #3

1. **Request place**: `{ coordinate: { latitude, longitude }, display_text }`; WGS84 and numeric bounds are explicit. No provider place ID, raw query, or unused search candidate.
2. **Filters**: independent `bus`, `metro`, and `youbike` selections; Walking is implicit and cannot be disabled as a connector.
3. **Departure setting**: a tagged union such as `depart_now`, `depart_at`, or `arrive_by`; absolute values use RFC 3339 with an offset.
4. **Locale**: BCP 47 request tag used for operator-authored variants and formatting context. Via-owned text is a semantic code with typed parameters, translated natively.
5. **Hierarchy**: result → ordered Journey Options → ordered Legs → static Guidance items. A Leg owns mode, endpoints, times, distance, geometry, boarding/alighting facts, and scoped Live Status.
6. **Geometry**: one named encoding with fixed precision and coordinate order; include Leg geometry and optionally a complete Journey Option overview.
7. **Live Status**: always expose the pinned `snapshot_id`, observation time, Freshness evaluation and reason. Keep scheduled and predicted/observed times distinct.
8. **YouBike**: expose pickup and return station action states and actual counts separately, with `unknown` distinct from zero and with observation/Freshness evidence. Never generate a plausible count.
9. **Outcomes**: HTTP status communicates transport/system class; stable code, typed parameters, field pointer, and scope communicate domain meaning. Empty result remains a successful domain outcome, not a malformed error.
10. **Evolution and refresh**: version the endpoint/schema and semantic-code catalog; prefer additive change and explicit deprecation. Refresh repeats the entire request, pins a new Network Snapshot, and atomically replaces all Journey Options.

## Final precedent split

**Copy structurally:** OTP labeled locations, itinerary/Leg organization, scheduled-versus-estimated time, semantic Guidance, scoped alerts, and translatable error codes; Google/Mapbox explicit time, locale, and geometry formats; Mapbox scoped machine warnings.

**Adapt:** MapKit native objects into provider-neutral selected coordinates/display text; Google transit-mode preferences into Via's independent product filters; OTP rental availability into actual, freshness-bearing YouBike evidence.

**Do not copy:** provider place IDs or raw addresses, exclusive top-level mode selectors, localized prose as a control-flow contract, implicit English fallback for Via-owned text, synthetic bike counts, predicted time as freshness proof, URL-carried Planning Request coordinates, partial Leg refresh, or pagination treated as refresh.
